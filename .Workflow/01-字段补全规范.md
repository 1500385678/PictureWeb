# 01-字段补全规范 · PictureWeb

> 字段补全流程。P1 light / P2 description 修复沉淀。

## 为什么需要这个文档

P1 light 89/390 空、P2 description 331/390 空,都是历史入库时没人填、没脚本补、AI 没接入导致的。
要避免下次再出"几百条空值靠人工补",必须把"补字段"这件事流程化。

## 字段分级

| 字段 | 重要性 | 空值容忍度 | 补全策略 |
|---|---|---|---|
| project / filename / abs_path | 必填 | 0 | 入库时就必须填,缺失即拒绝入库 |
| rel_path / file_hash / phash | 必填 | 0 | 入库脚本自动算,缺失即重新入库 |
| caption | 必填 | 0 | 文件名解析 + 人工微调,无 caption 不入库 |
| keywords | 必填 | 0 | 文件名解析 + 关键词库匹配,无关键词不通过 |
| scene / light / space / material / mood | 推荐 | ≤ 10% | 入库时尽量填,空值用 default 占位 |
| description | 可选 | 任意 | 降级为 caption+keywords,后续 AI 扩写 |
| arch_type / render_style / view_type | 可选 | 任意 | 关联表化,FTS5 同步 |
| color_palette / scale | 可选 | 任意 | AI 反推,无 key 时留空 |

## 补全顺序

1. **入库时**(`tools/ingest.py`,待建):必填字段缺失即报错
2. **空值兜底**(`tools/fill_description_default.py`):description 空 → caption+keywords 拼接
3. **AI 反推**(`tools/fill_light_gpt4v.py`):light 空 → GPT-4V 看图反推
4. **人工补录**:前端 UI 暴露 pending_tag=1 的记录,张勇手动填

## pending_tag 协议

- `pending_tag = 0`:已确认,无需补
- `pending_tag = 1`:AI 失败 / 数据缺失,需人工补录
- `pending_tag = 2`:人工已补,待 verifier 审核

前端应该只显示 `pending_tag >= 1` 的记录,让张勇专注补录。

## 跑批节奏

| 字段 | 频率 | 时机 | 脚本 |
|---|---|---|---|
| description 降级 | 一次性 | 入库后立即 | fill_description_default.py |
| light AI 反推 | 每周 | 周日 02:00 cron | fill_light_gpt4v.py |
| material AI 反推 | 每月 | 月初 02:00 cron | fill_material_gpt4v.py(待建) |
| arch_type 归一化 | 一次性 | 入库时 | ingest 脚本自动 |

## 不做什么

- 不批量 GPT 扩写 description(成本高、信号弱,降级已够用)
- 不在 FTS5 索引里加全字段(性能/相关性权衡,只加用户会搜的)
- 不把空值硬填一个 fake 值掩盖(比如 light 空填 'unknown',FTS5 反而会误中)
